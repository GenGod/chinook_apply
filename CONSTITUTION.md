# CONSTITUTION.md — Конституция проекта canada_job_search

**Версия:** 1.0 · **Принята:** 2026-09-16 · **Статус:** действует

Конституция — высший закон проекта. При любом конфликте побеждает она, затем
PROCESS.md / AGENTS.md, затем DESIGN.md, затем отдельные спеки. Ни один агент
(включая меня) не может отменить её статьи своей инициативой; изменения — только
через процедуру amendment (ст. 12).

---

## Статья 1. Человек в контуре

1.1. Любое исходящее наружу действие (отправка отклика, письма, изменение
публичных данных) требует явного Approve пользователя. Полный автопилот
запрещён независимо от зрелости системы.

1.2. Ни одно действие пользователя нельзя интерпретировать как постоянную
делегацию: Approve на один отклик не распространяется на следующий.

1.3. Сервис обязан перед отправкой показать пользователю полный пакет:
адаптированное резюме, cover letter, адресата и канал отправки.

## Статья 2. Правдивость резюме

2.1. Система не имеет права порождать факты. Каждый опыт, буллет, дата и цифра
в адаптированном резюме обязан маппиться на `data/profile/master_profile.json`.
Немаппируемое — дефект генерации, а не «улучшение».

2.2. Fact-check валидаторы — обязательный гейт. Провал = регенерация, при
повторном провале — остановка и эскалация пользователю.

2.3. `master_profile.json` — единственный источник правды о кандидате.
Изменить его может только пользователь; агент предлагает правки текстом,
применяет — человек.

## Статья 3. Безопасность и приватность

3.1. Секреты (API-ключи, SMTP-учётки, токены LLM) никогда не попадают в git,
логи, артефакты и метрики. Только `.env` / docker secrets.

3.2. PII (резюме, письма, контакты) хранится в изолированном хранилище
артефактов; в `event_log` и метриках — только ссылки и агрегаты.

3.3. Перед каждым merge обязателен security-аудит (`claude-security`);
найденные критические находки блокируют merge до исправления.

## Статья 4. Законность источников

4.1. Сбор вакансий — только официальные API, публичные RSS и публичные
страницы с соблюдением robots.txt и rate-limit. Скрейпинг LinkedIn запрещён
навсегда; обходимся источниками из DESIGN.md §2.

4.2. Идентификация запросов честная (UA, contact где требует API). Обход
капч и анти-бот защит запрещён.

4.3. Авто-отправка ограничена дневным лимитом (default 10) и jitter-задержками.
Ограничение можно только ужесточить без amendment.

## Статья 5. Спека прежде кода (SDD)

5.1. Ни одной строки прод-кода без принятой спеки в `specs/`. Тесты пишутся
до реализации (TDD), DoD спеки — критерий завершения инкремента.

5.2. Любое архитектурное решение, не покрытое DESIGN.md, сначала проходит
brainstorming и попадает в DESIGN.md (или spec), и только потом в код.

## Статья 6. Измеримость

6.1. Каждый LLM-вызов логируется: токены, стоимость, латентность, stage.
Незалогированный вызов — дефект.

6.2. Каждый инкремент отчитывается в `specs/notes/S<N>-report.md`: тесты,
security, токены. Отчёт — часть DoD, а не опция.

6.3. UI-изменения сопровождаются Playwright-снапшотами; деградация снапшота
без осознанного обновления — падение пайплайна.

## Статья 7. Недоверие к LLM-выводу

7.1. Вывод LLM — untrusted input до прохождения schema-валидации и
fact-check. Ничто из вывода не исполняется и не сохраняется как факт без
валидации.

7.2. Промпты версионируются вместе с кодом; изменение промпта проходит через
golden-set (S4) с контролем качества и стоимости.

7.3. Кэш по хэшу входа обязателен: одинаковые входы не оплачиваются дважды.

## Статья 8. Аудит и воспроизводимость

8.1. Все значимые события — в append-only `event_log` с timestamp и
исполнителем (user / agent / worker). Удаление записей запрещено.

8.2. Любой отправленный отклик восстановим по записям: вакансия → генерация →
approve → отправка → скриншоты.

## Статья 9. Простота и YAGNI

9.1. Этап 1 — один пользователь, один профиль. Мультипользовательские
абстракции не строятся «на будущее», если они не требуются текущей спекой.

9.2. Инфраструктура минимальна для текущей нагрузки; Postgres + Redis + два
процесса достаточно до обратного, доказанного метриками.

## Статья 10. Доступность и отказоустойчивость

10.1. Отказ одного источника не останавливает остальные (изоляция адаптеров).

10.2. Отказ отправки не теряет пакет: состояние `failed` сохраняет артефакты
и допускает retry по команде пользователя.

10.3. LLM-недоступность деградирует систему (пауза генерации), а не ломает
данные.

## Статья 11. Ответственная автоматизация браузера

11.1. Playwright-воркер действует только на явно подтверждённых откликах.

11.2. Каждый акт браузерной отправки документируется скриншотами «до» и
«после», прикреплёнными к `dispatch_log`.

11.3. Столкновение с капчей/анти-ботом = немедленная остановка попытки и
fallback на ручную отправку. Повторные попытки обхода запрещены.

## Статья 12. Изменение конституции

12.1. Право предложить amendment есть у любого агента, право принять — только
у пользователя.

12.2. Amendment получает версию (1.x), дату и запись в changelog ниже.
Ослабление статей 1–4 и 11 обратно запрещено (replace-only tightening).
