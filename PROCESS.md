# PROCESS.md — Процесс разработки canada_job_search

**Версия:** 1.1 · **Дата:** 2026-09-16

Определяет, *как* идёт работа над проектом: полный цикл от идеи до merge,
гейты качества, роли, модели, ритм, обработку инцидентов. Иерархия документов:

```
CONSTITUTION.md          — непереоцениваемые принципы (статьи 1–12)
  └─ PROCESS.md          — этот документ: жизненный цикл и гейты
       └─ AGENTS.md      — мандатные инструменты (плагины) по этапам
            └─ DESIGN.md — архитектура решения
                 └─ specs/S*.md — спецификации инкрементов
                      └─ specs/notes/S*-report.md — отчёты по инкрементам
```

Конфликт разрешается в пользу верхнего документа. Изменить PROCESS.md может
агент по команде пользователя; изменения фиксируются в changelog.

---

## 1. Роли

| Роль | Кто | Полномочия |
|---|---|---|
| Product Owner | Пользователь | Approve спек, Approve отклика (ст. 1), amendment конституции, approve стека, финальное «принято» по инкременту |
| Architect | Модель GLM-5.3 (см. §2) | Brainstorming, спеки, планы, ревью решений и кода, security-решения |
| Implementer | Модель GLM-5.3-flash (см. §2) | Написание кода и тестов по принятому плану, рефакторинг, фиксы |
| Automation | Воркеры сервиса | Ingestion, генерация, dispatch — строго в рамках статей 1–4, 11 |

## 2. Модели и маршрутизация

На проекте ровно два типа моделей:

| Тип | Модель | Назначение |
|---|---|---|
| Архитектор | **GLM-5.3** | Решения: brainstorm, спеки, планы, дизайн-ревью, код-ревью, security-аудит, трактовка конституции |
| Имплементатор | **GLM-5.3-flash** | Исполнение: код по плану, тесты, рефакторинг, массовые механические правки |

Правила маршрутизации:
- Все этапы E1–E2 (brainstorm, spec), E3 (plan) и все ревью/аудиты (G3–G5,
  code review) выполняет Архитектор.
- E4–E5 (red tests, implement) выполняет Имплементатор под планом Архитектора.
 Имплементатор не принимает архитектурных решений: столкнулся с пробелом
  плана — эскалация Архитектору, а не импровизация.
- Продуктовый LLM-шлюз (runtime) наследует тот же принцип: скоринг вакансий —
  flash (дёшево, массово), генерация резюме/писем — основная модель
  (quality-critical). Точный маппинг stage→model — в DESIGN.md §4.1.
- Метрики токенов/стоимости в отчётах инкрементов разбиваются по типу модели.

## 3. Единица работы

Единица планирования — **инкремент = одна спека** (реестр и порядок —
DESIGN.md §6.1; расширяется через [BACKLOG.md](./BACKLOG.md), откуда фичи
после G0 получают номера спек — как S1a из B-001). Инкремент неделим:
не начинаем S(n+1), пока S(n) не закрыта отчётом (исключение — явное
решение PO).

## 4. Конвейер инкремента

```
Idea → [G0 Intake] → Brainstorm → Spec draft → [G1 Spec review] →
Plan → [G2 Plan review] → Red tests → Implement (LSP) →
[G3 Green & clean] → UI до/после + E2E → [G4 UI gate] →
Security audit → [G5 Security gate] → Docs & report → [G6 Done] → Merge
```

### Этапы и обязательные инструменты (детализация AGENTS.md)

**E0. Intake [G0].** Формулируется задача. Проверка: не противоречит ли
конституции и DESIGN.md. Если противоречит — стоп и эскалация PO.

**E1. Brainstorm (Архитектор).** Обязателен `superpowers:brainstorming`.
Выход: 2+ альтернативы, trade-offs, выбор. Выбор фиксируется в спеке.

**E2. Spec draft → [G1] (Архитектор).** Файл `specs/S<N>-<name>.md` по
шаблону §6. PO одобряет спеку текстом. Без одобрения G1 код не начинается
(ст. 5.1).

**E3. Plan → [G2] (Архитектор).** `superpowers:writing-plans`: декомпозиция
на шаги с критерием проверки; план в `specs/plans/S<N>-plan.md`. План
пишется под Имплементатора: входы, выходы и границы каждого шага explicit.

**E4–E5. TDD-цикл (Имплементатор).**
- Разработка идёт **исключительно по TDD**: red → green → refactor.
- Red: сначала падающий тест по acceptance-критерию; прод-кода,
  покрывающегося этим тестом, ещё не существует.
- Green: минимальный код, чтобы тест прошёл.
- Refactor: обязательный шаг; чистится и код, и тест — под LSP-диагностикой
  (`typescript-lsp`), с `context7` перед любой новой зависимостью.
- Прод-код, попавший в коммит без предшествующего красного теста, —
  нарушение процесса и ст. 5.1 конституции.

**E6. [G3 Green & clean].** Все тесты зелёные, tsc strict — 0 ошибок,
линт и arch-lint чисты (см. §7).

**E7. UI до/после → [G4].** Обязателен для **каждой** итерации:
- **До** (baseline): на старте ветки снимается полный набор снапшотов
  ключевых экранов с `main`.
- **После**: те же экраны на ветке инкремента.
- Diff «до/после» прикладывается к отчёту: если UI не должен был меняться —
  фиксируется отсутствие диффа (это и есть регрессионная проверка backend-only
  итераций); если менялся — дифф осознанно одобряется.
- Инструменты: `superdesign` + `frontend-design` при создании/изменении
  экранов, `chrome-devtools-mcp` для отладки, Playwright для снапшотов/E2E.
- Снапшоты хранятся в **git-lfs** (см. §8) — бинарные PNG не раздувают git.

**E8. Security audit → [G5] (Архитектор).** `claude-security` + машинные
сканеры (`npm audit`, secret-scan). Критические находки — блокер (ст. 3.3).

**E9. Docs & report → [G6 Done].** Обновление DESIGN.md при архитектурных
изменениях; отчёт `specs/notes/S<N>-report.md` (тесты цифрами, UI-дифф,
security, токены по моделям на golden-set при затронутом LLM);
`superpowers:verification-before-completion`. После — merge.

## 5. Гейты: максимум машинного, минимум человеческого

Принцип: **любая проверка, которую можно автоматизировать, обязана быть
машинным гейтом** — человеку остаются только решения о продукте и ценности.
Ручные проверки запрещено дублировать машине и наоборот.

| Гейт | Тип | Машинная часть (blocking) | Человеческая часть |
|---|---|---|---|
| G0 | агент | Чек-лист соответствия конституции | — |
| G1 | human | — | PO одобряет спеку |
| G2 | агент+PO | План существует, шаги имеют критерии | PO вправе смотреть план |
| G3 | machine | unit/integration зелёные; tsc strict 0; eslint 0; **arch-lint 0**; coverage не упал | — |
| G4 | machine | Playwright E2E; визуальный diff до/после (изменение = осознанный update снапшота) | PO смотрит дифф ключевых экранов |
| G5 | machine+agent | `npm audit`, secret-scan, gitleaks-подобные проверки; `claude-security` аудит | — |
| G6 | human | Отчёт существует и заполнен (наличие проверяется скриптом) | PO принимает инкремент |

Расширение набора машинных гейтов — приоритетная задача каждого milestone:
как только проверка в отчёте выполняется руками второй раз подряд, она
кандидат на автоматизацию в CI.

## 6. Шаблон спеки `specs/S<N>-<name>.md`

```markdown
# S<N>: <название>
Статус: draft | accepted | done · Версия: 1.0 · Milestone: M<k>
## Проблема и цель
## Входные артефакты / зависимости
## Решение (выбранная альтернатива из brainstorm + почему отвергнуты остальные)
## Контракт (типы, схемы, API — конкретика)
## Acceptance criteria (проверяемые утверждения)
## Тест-план (unit / integration / golden-set / e2e / snapshots до-после)
## Метрики (что и как меряем по DESIGN.md §5)
## DoD (чеклист, копируется в отчёт)
## Открытые вопросы
```

## 7. Архитектурный линтер (arch-lint)

Для поддержания точной архитектуры обязателен ESLint-плагин
`packages/eslint-plugin-arch`, проверяющий границы из DESIGN.md:
- direction of dependencies: `apps/*` → `packages/*` (обратное запрещено);
- `packages/adapters` не импортирует `generation`/`dispatch`;
- UI не обращается к БД/очередям напрямую, только через API/контракты;
- запрещённые импорты (например, `llm` вне gateway).

Если готового плагина в общем доступе нет — **разрабатываем свой**
(спека S0, milestone M1). Arch-lint входит в G3 с момента появления
репозитория: ни один merge с нарушением границ невозможен. Правила границ
меняются только вместе с изменением DESIGN.md.

## 8. Стек и git-дисциплина

### 8.1 Заморозка стека
- Используем максимально современный стек на момент старта (S0), после чего
 **жёстко фиксируем** его в `STACK.md` (точные версии runtime, ключевых
  библиотек, Node, Playwright, CI-образов) + lockfiles в git.
- Изменение любой позиции стека — только по необходимости и **строго после
  ручного одобрения PO**: мотивация (security-fix / критичная фича /
  EOL) оформляется записью в changelog `STACK.md`.
- Авто-обновления зависимостей запрещены; отчёты об обновлениях
  (dependabot/renovate, если включаем) — report-only, без auto-merge.

### 8.2 Git
- `main` — всегда зелёная. CI: lint → arch-lint → typecheck → unit →
  integration → e2e → visual diff.
- Ветка на инкремент: `feat/S<N>-<name>`; фиксы — `fix/...`.
- Commit: `S<N>: <что и почему>` — номер спеки обязателен.
- Merge только после G6.
- **Git-LFS обязателен** для `*.png`-снапшотов (и любых бинарных артефактов
  тестов): `tests/__snapshots__/**` — в `.gitattributes` под LFS. Настройка
  LFS — часть спеки S0.
- До появления CI (S0) его роль исполняет локальный прогон полного набора
  проверок перед merge, зафиксированный в отчёте.

## 9. Инциденты, баги и регрессионные тесты

| Ситуация | Действие | Эскалация PO |
|---|---|---|
| Найден баг (в тестах, коде, промптах) | **Сначала — красный воспроизводящий тест**, затем фикс. Случай навсегда остаётся в сьюте | Нет, но в отчёте |
| Провал fact-check дважды (ст. 2.2) | Стоп генерации | Да |
| Капча/анти-бот при dispatch (ст. 11.3) | Стоп попытки, fallback ручной | Да |
| Источник пуст/ломается | Алерт в метриках, isolate (ст. 10.1) | Нет, но в отчёте |
| LLM недоступна | Пауза генерации, retry с backoff (ст. 10.3) | Нет |
| Security-находка критическая | Блокер merge | Да |
| Любое сомнение в трактовке конституции | Стоп | Да |

Правило багфикса: «нет красного теста — нет фикса». В отчёте инкремента
считается `bugfixes: N, regression cases added: N` — числа обязаны совпадать
(исключение — фиксы в документации).

Stop-work правило: при конфликте «удобно» vs «конституция» работа
останавливается до решения PO.

## 10. Метрики: кто и когда собирает

- **Токены/стоимость** — LLM-шлюз в runtime, разбивка по типу модели
  (архитектор/имплементатор; flash/main в runtime); в отчёте инкремента —
  прогон golden-set.
- **Качество генерации** — факт-чек в runtime + thumbs/правки PO в UI;
  агрегат в отчёты M2+.
- **Воронка и здоровье** — SQL-вьюхи поверх `event_log`; страница Metrics
  появляется в S10.
- **Снапшоты UI до/после** — на каждую итерацию (§4 E7), хранение в LFS.

Метрика, которую никто не посмотрел в двух последовательных отчётах, либо
упрощается, либо удаляется (ст. 9 YAGNI).
