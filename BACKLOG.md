## B-001 · Список найденных вакансий с откликом по прямой ссылке

- **Статус:** accepted → запланировано как **S1a** (внутрь M1, сразу после S1)
- **Приоритет:** now
- **Автор:** PO (2026-09-16)

### Суть
Экран «Jobs» — таблица найденных вакансий с возможностью мгновенно
откликнуться вручную по прямой ссылке на оригинал.

### Функциональность
- Список вакансий из БД: title, employer, location, source, зарплата (если
  есть), дата находки, canonical-дедуп уже применён.
- Колонка/кнопка **«Apply externally»** — прямая ссылка `job.url` на
  исходную вакансию (открывается в новой вкладке, rel=noopener).
- Отметка «я откликнулся вручную»: кнопка рядом помечает вакансию
  `applied_manually` — пишется в `event_log` и статус `application`,
  чтобы воронка-метрики (DESIGN.md §5.3) не теряла ручные отклики.
- Базовые фильтры: источник, дата, зарплатная вилка; сортировка по дате.
- Read-only: никакого approve-флоу, никакого редактирования — это ранний
  облегчённый экран, полноценный Inbox остаётся в S7.

### Зависимости
- S1 (нормализованные вакансии в Postgres) — обязательна.
- S2 (rule-фильтры) и всё далее — не нужны; score-колонка добавится в S4
  без изменения контракта экрана.

### G0-проверка
Конфликтов с конституцией нет: экран только читает данные и ссылается
наружу; ручная отметка отклика — явное действие пользователя (ст. 1.1
соблюдена по определению).

### Оценка
Малый инкремент: один read-only экран + один PATCH-эндпоинт + event_log
запись. Дизайн по общему правилу: `superdesign` → `frontend-design` →
снапшоты до/после (E7), E2E на фильтры и отметку.

## B-002 · Мульти-резюме: суперпрофиль и расширение охвата позиций

- **Статус:** accepted → запланировано как **S11** (новый milestone **M5**)
- **Приоритет:** next (после закрытия M2 — генерация должна уже работать)
- **Автор:** PO (2026-09-16)

### Суть
Собрать несколько резюме пользователя (DOCX/PDF/LinkedIn-экспорт),
извлечь максимально широкий суперсет знаний, навыков и обязанностей и
использовать его как расширенную базу для (а) генерации резюме под
конкретную вакансию и (б) предложения как можно большего числа подходящих
позиций.

### Функциональность
1. **Ingest резюме:** загрузка N документов; парсинг → структурированные
   факты (опыт, скиллы, обязанности, образование, сертификаты) с
   **provenance** — каждый факт знает, из какого документа и какой строки
   он пришёл.
2. **Слияние в суперпрофиль:** дедупликация фактов (fuzzy), разрешение
   конфликтов (расходящиеся даты/титулы — очередь решений для PO).
   Результат — **предложение** нового `master_profile.json` (v2); применяется
   только после явного approve PO (конституция ст. 2.3). Ничего не
   выдумывается: каждый факт прослеживается до исходного документа.
3. **Резюме-треки (personas):** из суперпрофиля собираются канонические
   варианты-акценты, например «Senior FullStack TS/Node/React»,
   «Frontend Infrastructure / Build Systems», «AI Engineer»,
   «.NET Enterprise Lead». Генерация (S5) выбирает лучший трек под вакансию
   и адаптирует уже его.
4. **Расширение охвата позиций:** на основе суперпрофиля пересматривается
   taxonomy поиска — дополнительные NOC-коды и title-семейства (решение о
   конкретных кодах — за PO, с обоснованием по фактам профиля). Матчинг
   (S2/S4) получает ранжирование по трекам: вакансия оценивается против
   всех треков.
5. **Fact-check v2:** валидаторы (DESIGN.md §4.2) проверяют сгенерированное
   против суперпрофиля с provenance — то же правило «не порождать факты»,
   но на более широкой базе.

### Зависимости
- S4 (LLM-скоринг) и S5 (генерация) — обязательны: фича расширяет работающий
  пайплайн, а не создаёт его.
- Схема профиля v2 (provenance-поля) — миграция `master_profile.json`.
- Новые таблицы: `profile_source`, `profile_fact` (см. DESIGN.md §3.2).

### G0-проверка
- Ст. 2 (правдивость): суперпрофиль = объединение документов пользователя,
  агент не добавляет фактов сам; конфликты решает PO.
- Ст. 2.3: merge применяется только после approve PO.
- Ст. 9 (YAGNI): треки не множатся сверх подтверждённых данных; пустые
  треки не создаются.
- Расширение NOC — отдельное явное решение PO, не автоматика.

### Оценка
Крупный инкремент: парсинг + слияние + UI просмотра диффа профиля и
очереди конфликтов + миграция матчинга/генерации на треки. Реализует
«глубокий анализ резюме» из DESIGN.md §1.3 (перенесено в roadmap).

## B-005 · Контейнеризация планировщика

- **Статус:** idea
- **Приоритет:** later
- **Автор:** процесс S12 (R6)

Dockerfile (node:26-alpine + pnpm + tsx) и compose-сервис scheduler, чтобы сбор шёл сам при
поднятом Docker Desktop, без живого терминала. Требует docker-build шага в CI. Не смешивать
с логикой планирования (S12 закрыт без контейнера по решению PO).
